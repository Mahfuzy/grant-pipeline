# grant-pipeline

The data layer for **Fundscout**. It collects grant opportunities from trusted public sources, extracts them into a structured schema, normalises and deduplicates them, and tracks how they change over time. `SPEC.md` is the source of truth for scope and design.

> Status: **Milestones 0–7 built.** Sources are collected politely on a schedule. Documents are extracted (field mappings or an LLM), normalised, deduplicated and merged into grant records with change history and a review queue. An internal API and a small admin UI sit on top. Only the two confirmed sources are configured; more are added through the process in [Adding a source](#adding-a-source).

## Prerequisites

- [uv](https://docs.astral.sh/uv/) (it installs Python 3.12 for you)
- Docker with the Compose plugin

## Setup

```bash
# 1. Install Python 3.12 and all dependencies (creates .venv/)
uv python install 3.12
uv sync

# 2. Create your local config
cp .env.example .env        # then edit values as needed

# 3. Start Postgres 16
docker compose up -d db
docker compose ps           # wait until "db" shows (healthy)

# 4. Create the schema and load the taxonomy
uv run fundscout db upgrade
uv run fundscout taxonomy seed

# 5. Register the sources and run one
uv run fundscout sources sync --dir sources     # or: sources add --file sources/<name>.yaml
uv run fundscout run --source grants_gov --limit 5
uv run fundscout sources list
```

To run the whole stack in Docker (Postgres, a setup job that migrates, seeds and syncs sources, the scheduler worker, and the API with the admin UI):

```bash
docker compose up -d --build
docker compose logs -f worker
open http://localhost:8000/admin/     # API_KEY from .env
```

The containers read `.env` (API_KEY, CONTACT_EMAIL, LLM settings). Note that the worker then collects for real on each source's schedule, and uses the LLM (and spends tokens) if one is configured.

Set `CONTACT_EMAIL` in `.env` before collecting: it is sent in the User-Agent so site owners can reach you.

Optional: if a source needs JS rendering, install the browser extra:

```bash
uv sync --extra browser
uv run playwright install chromium
```

To stop everything: `docker compose down`. Add `-v` to also delete the database and raw-snapshot volumes.

## Database and migrations

The schema is managed with Alembic (`alembic/`); models live in `src/fundscout/db/models.py`.

```bash
uv run fundscout db upgrade                              # apply all migrations
uv run alembic revision --autogenerate -m "describe"     # after changing models
uv run alembic check                                     # fails if models and migrations differ
```

Enum-like columns (statuses, review reasons, etc.) are stored as VARCHAR with a CHECK constraint, so adding a value is an ordinary autogenerated migration.

## Taxonomy

Themes, regions, organisation types and grant types are seeded from YAML files in `src/fundscout/taxonomy/data/`. Those files are the source of truth. To change the taxonomy, edit the YAML and run:

```bash
uv run fundscout taxonomy seed
```

Seeding is idempotent. It matches rows by `slug`, updates labels, parents and country lists in place, and warns about (but never deletes) rows that are no longer in YAML. Each entry has a `slug`, a `label`, an optional `parent` slug, and for regions only, a list of ISO 3166-1 alpha-2 `countries`. Quote country codes, because unquoted `NO` is read as `false` in YAML. A parent region automatically covers its sub-regions' countries. The sub-regions follow the UN M49 geoscheme; see the header of `regions.yaml` for the deviations and for how `global-south` is defined.

## Collecting from sources

Sources are defined in YAML files under `sources/` and loaded into the database:

```bash
uv run fundscout sources add --file sources/<name>.yaml   # add, or update if the name exists
uv run fundscout sources list                             # status and last run
uv run fundscout run --source <name> [--limit N] [--force]
uv run fundscout run-all                                  # all enabled sources with terms_reviewed
```

A run discovers items, fetches each document and stores it as a raw snapshot in `RAW_STORAGE_DIR`, recorded in `raw_documents`. If a document's content hash matches the previous snapshot, or the server answers 304, only `last_checked_at` is updated. Each run is logged in `source_runs` with its counts and errors. A failing item is recorded and the run moves on.

Responsible collection is built in. Each request:
- checks robots.txt (RFC 9309)
- respects a per-domain rate limit (default 3 s; `rate_limit_seconds` per source)
- retries 429/5xx with backoff and honours `Retry-After`
- uses conditional requests (ETag / Last-Modified)
- identifies itself with a User-Agent that includes `CONTACT_EMAIL`

Sources with `terms_reviewed: false` or `enabled: false` only run with `--force`, and the scheduler never runs them.

### Current sources

| Source | Adapter | Notes |
|---|---|---|
| `grants_gov` | `generic_api` | Grants.gov search2 API, posted and forecasted opportunities. Details come from `fetchOpportunity`, but only when an opportunity's search result changes or its snapshot is more than 7 days old. Responses carry a per-request `token` and randomly ordered lists, so the change hash is computed over canonical JSON. |
| `edctp3` | `generic_html_listing` | Global Health EDCTP3 calls listing, all pages. Most calls link to the EU Funding & Tenders Portal. Those pages need JavaScript, so the topic's public JSON is fetched instead. EDCTP3 `/document/` pages are fetched as the PDF they wrap. Uses a 10 s rate limit because the site returns 429 at 3 s. |

### Adding a source

Most sources need only a YAML file; see `sources/*.yaml` for complete, commented examples. The process:

1. **Confirm the source with the project owner.** Prefer an official API or RSS feed over scraping (SPEC §9), and collect only public pages: no logins, paywalls or anti-bot workarounds.
2. **Check robots.txt and the terms of use.** Record what you found, with the date, in the source's `notes`. Leave `terms_reviewed: false` until the terms have been reviewed. Until then the scheduler skips the source, and manual runs need `--force`.
3. **Pick an adapter and write `sources/<name>.yaml`:**
   - `generic_api`: a JSON search endpoint with offset pagination, a canonical `item_url` per hit, and an optional per-item `detail` request. Templates like `"{id}"` take values from the hit.
   - `generic_rss`: a feed URL. Each entry's link is fetched.
   - `generic_html_listing`: a listing URL, CSS selectors for items and detail links, optional extra fields, a `<dl>` capture, and next-link pagination.
   - Write a custom adapter (in `src/fundscout/sources/adapters/`, registered in `registry.py`) only if config can't express the source.

   Options every adapter accepts:
   - `rate_limit_seconds`
   - `content_hash`: `raw`, `json` (drop keys and sort lists) or `html` (hash one element only)
   - `reject_markers`: text that marks a block page served as 200
   - `refetch_unchanged_after_days`
   - `url_rewrites`: map a link to a canonical identity URL and a different fetch URL
   - `primary_source: true` if the source is the funder's own official channel (its values win merges)
   - `extraction`: rules choosing `mapping`, `ft_topic`, `rules`, `llm` or `skip` per URL or content type, plus `date_order` and `funder_country` for normalisation
4. **Set `schedule`** (cron, evaluated in UTC); leave it out for manual-only sources.
5. **Try it without writing grants:**
   ```bash
   uv run fundscout sources add --file sources/<name>.yaml
   uv run fundscout run --source <name> --limit 3 --no-extract --force   # fetch only
   uv run fundscout reprocess --source <name> --limit 3                  # extract what was stored
   ```
6. **Save fixtures and add tests.** Save real responses under `tests/fixtures/<name>/` and add adapter tests that run on them, so tests never hit the network. Add a few hand-labelled documents to `tests/fixtures/eval/labels.yaml` and run `fundscout eval-extraction`.
7. **Set `terms_reviewed: true`** once the terms are reviewed, then `fundscout sources sync`. The worker picks the change up within 5 minutes.

Candidate sources named in SPEC §10 but **not yet configured** (awaiting the owner's confirmation):
- the EU Funding & Tenders Portal search API, which would cover every EU programme and reuse the `ft_topic` extractor;
- foundation websites relevant to the target region.

## Extraction

New or changed documents are extracted during a run, and the results are stored in `extraction_results`:
- all grants found in the document
- the issues found while normalising them
- LLM token usage

How a document is extracted is set per source under `config.extraction.rules`. The first rule whose `match_url` / `match_content_type` matches wins, and the default is the LLM.

| Extractor | Use | Notes |
|---|---|---|
| `mapping` | JSON APIs | Config-driven field paths with fallbacks, constants and templates. `grants_gov` uses it. |
| `ft_topic` | EU Funding & Tenders Portal topic JSON | Shared by every EU programme on the portal. |
| `rules` | HTML with stable markup | CSS selectors per field. |
| `llm` | Everything else (HTML pages, PDFs) | See below. |
| `skip` | Documents that should not be extracted | |

**LLM extraction** uses structured outputs from the provider set by `LLM_PROVIDER`:
- **Anthropic** (default): credentials come from `ANTHROPIC_API_KEY` or an `ant auth login` profile.
- **Groq**: set `LLM_PROVIDER=groq` and `GROQ_API_KEY`. Output is constrained with Groq's JSON-schema mode. Strict mode works only on some Groq models (see Groq's structured-output docs); set `GROQ_STRICT_OUTPUT=false` for others.
- **Model:** `EXTRACTION_MODEL`, in the provider's naming (e.g. `claude-sonnet-5` or `openai/gpt-oss-120b`). Check a new provider or model with `EXTRACTION_MODEL=... LLM_PROVIDER=... GROQ_API_KEY=... uv run pytest -m live -k llm`, then `fundscout eval-extraction --force-llm` (both cost tokens).
- **Input:** the page's main content (not raw HTML) or the PDF text, plus the URL, today's date and the listing's description of the document. Very long documents are shortened: the opening is kept, plus paragraphs about deadlines, eligibility and amounts. Shortening is always logged and recorded.
- **Taxonomy:** allowed slugs are in the prompt, and anything outside the taxonomy is dropped afterwards.
- **Validation:** invalid output gets one retry with the error. After that an `extraction_failed` review item is created.
- **Unreadable documents** (e.g. a corrupt PDF) also become review items. The raw snapshot is always kept.
- **No model or credentials:** LLM documents are skipped with a warning, not failed.
- **Token usage** is logged per call and totalled in each run's summary log line.

**Normalisation** (`src/fundscout/normalise/`) handles:
- currencies (symbols and words to ISO 4217; a bare `$` is USD only for US funders or US context, otherwise flagged ambiguous)
- amounts (`up to $50,000`, `£10k–£25k`, `USD 1.5 million`)
- dates (`31st March 2027`, and `03/04/2027` using the source's `date_order`)
- countries (to ISO alpha-2)
- taxonomy values, matched by slug, label or `aliases` in the taxonomy YAML

Anything dropped or ambiguous is recorded as an issue on the extraction result. `low_confidence`, `ambiguous_currency` and `missing_required_fields` issues also become review items.

```bash
uv run fundscout run --source edctp3 --no-extract   # fetch only
uv run fundscout reprocess --source edctp3          # re-extract stored documents, no fetching
```

### Running the extraction eval

`tests/fixtures/eval/labels.yaml` is a hand-labelled set of 11 documents and 14 grants from both sources. Values were read from the documents themselves.

```bash
uv run fundscout eval-extraction              # configured extraction; LLM documents need credentials
uv run fundscout eval-extraction --no-llm     # structured documents only
uv run fundscout eval-extraction --force-llm  # every document through the LLM (costs tokens)
```

It prints per-field accuracy and every mismatch. Only fields present in a label are scored. Titles must match almost exactly after normalisation, so a truncated title counts as wrong. Funder names may also differ by extra words (e.g. "Joint Undertaking"). Amounts, dates and enums must be equal.

## Grants: matching, merging, history and review

Each extracted grant is matched to an existing one (`src/fundscout/dedup/`, SPEC §8.1). Matching is tried in this order:
1. **Same link:** the same source, URL and item.
2. **Fingerprint:** hash of normalised funder + normalised title + closing date.
3. **Fuzzy:** same funder, title `token_set_ratio` ≥ `DEDUP_MATCH_THRESHOLD`, and closing dates within `DEDUP_DATE_TOLERANCE_DAYS`.
4. **Near miss:** a score between the two thresholds creates a new grant plus a `possible_duplicate` review item.

Two special cases:
- **Separate listings:** different URLs in the same source are treated as different grants and never merged.
- **Multi-grant documents:** when one document describes several grants (e.g. a call PDF with four topics), each grant gets its own `grant_sources` row, keyed by its title (`item_key`).

When a grant appears in several sources, `grant_sources` links it to each one:
- **A primary source wins.** When a source flagged `primary_source` (the funder's own channel) lists the grant, its values win. Other sources only fill empty fields.
- **No primary source:** the most recent value wins. If sources disagree on the closing date or amount, a `conflicting_values` review item is opened.
- **Manual edits stick.** Fields corrected through the API or UI are never overwritten by the pipeline.

Every update writes field-level diffs to `grant_changes`. A new grant gets a `created` row, and status changes are recorded too. A changed deadline always opens a `deadline_changed` review item.

Status follows SPEC §6.3 and is recomputed on every update and daily by the worker (`fundscout refresh-status` runs it by hand).

After each complete, error-free run (not `--limit` runs, and not when the listing shrank to under half of the previous run's), grants that are missing from a source's listing have `missing_count` incremented. After `MISSING_RUNS_BEFORE_REVIEW` runs a `possibly_removed` item is opened. Grants are never closed just because they disappeared, and grants that are already closed are not flagged. After `FETCH_FAILURES_BEFORE_REVIEW` consecutive failed runs, the source gets a `fetch_failed_repeatedly` item and an `ALERT` log line.

## Scheduling

```bash
uv run fundscout worker        # or the `worker` service in docker compose
```

The worker (APScheduler) runs each source on its `schedule` (cron, UTC):
- It only schedules sources that are enabled and have `terms_reviewed: true`.
- It re-reads the sources table every 5 minutes, so changes need no restart.
- It never runs one source twice at once, and collapses missed runs into one.
- It recomputes grant statuses daily at 00:10 UTC.

## API and admin UI

```bash
uv run fundscout api            # http://127.0.0.1:8000, OpenAPI docs at /docs
```

Every endpoint except `/health` needs the `X-API-Key` header, which must equal `API_KEY`. Without an `API_KEY` configured, the API refuses requests.

| Endpoint | |
|---|---|
| `GET /grants` | Filters: `status` (repeatable), `theme`, `region`, `country`, `org_type`, `closing_before`, `closing_after`, `q` (full-text), `needs_review`, `funder`, `sort`, `page`, `page_size`. `region` also matches grants tagged with a country in that region, and `country` matches grants tagged with a region containing it. |
| `GET /grants/{id}` | Grant with sources, taxonomy, change history and review items |
| `PATCH /grants/{id}` | Manual correction, recorded in `grant_changes` as `manual` (with `changed_by`) and protected from pipeline updates; `release_overrides` hands fields back |
| `GET /changes?since=` | Change feed (default: last 7 days) |
| `GET /sources`, `GET /sources/{id}/runs`, `POST /sources/{id}/run` | Source status and run history; start a run in the background (`force=true` bypasses the enabled/terms checks) |
| `GET /review?status=open&reason=`, `GET /review/{id}` | Review queue; the detail view includes the grant, the source document and the latest extraction output |
| `POST /review/{id}/resolve`, `POST /review/{id}/dismiss` | Body: `{"resolved_by": ..., "note": ...}` |
| `GET /taxonomy` | Slugs and labels |
| `GET /health` | Database check |

The admin UI (`admin-ui/`, React + Vite + TypeScript) has three screens:
- **Review queue:** extracted values side by side with the stored grant, a link to the source document, and resolve / edit / dismiss actions.
- **Grants:** search and filters, plus a detail view with sources and history.
- **Sources:** status, runs and errors, and a "Run now" button.

The API serves the built UI at `/admin`:

```bash
cd admin-ui && npm ci && npm run build     # served by `fundscout api` at /admin
npm run dev                                # dev server on :5173, proxying to the API on :8000
```

The UI asks for the API key and keeps it in the browser's localStorage.

## Tests and lint

The database tests use a separate database, `fundscout_test`, on the Compose Postgres. It is created and reset automatically. Override it with `TEST_DATABASE_URL`. If Postgres isn't reachable, the database tests are skipped.

```bash
uv run pytest               # unit tests; never hit the network or the real LLM API
uv run pytest -m live       # opt-in live integration tests
uv run ruff check .
uv run ruff format --check .
uv run mypy
```

## Environment variables

All settings are read from the environment or `.env` (see `src/fundscout/config.py`). `.env.example` lists every setting.

| Variable | Default | Purpose |
|---|---|---|
| `DATABASE_URL` | `postgresql+psycopg://fundscout:fundscout@localhost:5432/fundscout` | SQLAlchemy connection string |
| `TEST_DATABASE_URL` | `postgresql+psycopg://fundscout:fundscout@localhost:5432/fundscout_test` | Database used by the test suite (wiped on each run) |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` / `POSTGRES_PORT` | `fundscout` / `fundscout` / `fundscout` / `5432` | Used by `docker-compose.yml` only |

| `ANTHROPIC_API_KEY` | none | Anthropic API key (or use an `ant auth login` profile) |
| `GROQ_API_KEY` | none | Groq API key (when `LLM_PROVIDER=groq`) |
| `GROQ_BASE_URL` | `https://api.groq.com/openai/v1` | Groq API base URL |
| `GROQ_STRICT_OUTPUT` | `true` | Strict JSON-schema output; set `false` for Groq models that don't support it |
| `EXTRACTION_MODEL` | none | Model used for LLM extraction, in the provider's naming; unset disables LLM extraction |
| `CONTACT_EMAIL` | `change-me@example.com` | Contact address included in the crawler User-Agent |
| `DEFAULT_RATE_LIMIT_SECONDS` | `3.0` | Minimum seconds between requests to the same domain |
| `HTTP_TIMEOUT_SECONDS` | `30` | HTTP request timeout |
| `RAW_STORAGE_DIR` | `data/raw` | Where raw snapshots are stored |
| `DEDUP_MATCH_THRESHOLD` | `90` | Fuzzy title score at or above which two grants are treated as the same |

| `DEDUP_DATE_TOLERANCE_DAYS` | `31` | Closing dates further apart than this block a fuzzy match (e.g. next year's round) |
| `REVIEW_LOW_CONFIDENCE_THRESHOLD` | `0.6` | Field confidence below which a `low_confidence` review item is raised |
| `MISSING_RUNS_BEFORE_REVIEW` | `3` | Consecutive missed runs before a `possibly_removed` review item is raised |
| `FETCH_FAILURES_BEFORE_REVIEW` | `3` | Consecutive failed runs before a `fetch_failed_repeatedly` review item is raised |
| `API_KEY` | none | `X-API-Key` value for the internal API; unset means the API refuses requests |
| `ADMIN_UI_DIR` | `admin-ui/dist` | Built admin UI served at `/admin` |
| `API_PORT` | `8000` | Host port for the `api` service in docker compose |
| `LOG_LEVEL` | `INFO` | Log level |
| `LOG_JSON` | `true` | Output JSON-structured logs |
